# Mercury deployment

The supplied brief requires Mercury. No account details, school server address, database credentials, SSH/SFTP access or assigned URL were supplied. This guide prepares the files; actual deployment must use the university account and be verified there. Do not replace the required Mercury URL with another provider.

## Confirm host support first

Use the course's Mercury instructions to confirm the web root and permissions. The prepared adapter requires PHP 8.1+ with PDO and either PDO SQLite or PDO MySQL. Confirm which database the account permits. If neither is available, ask the tutor for the supported REST backend arrangement. Do not assume the school runs Node.js or permits background processes.

## Build

```sh
npm ci
npm run build:mercury
```

This emits `build/mercury/index.html`, `assets/`, `.htaccess` and `api.php`. Hash routes and relative Vite asset paths support hosting inside a subfolder. The PHP API uses query-string routing such as `api.php?path=/events`, avoiding dependence on URL rewrite rules. See the official [Vite static deployment guide](https://vite.dev/guide/static-deploy.html) and [Vue Router history-mode documentation](https://router.vuejs.org/guide/essentials/history-mode.html).

## Recommended directory arrangement

Adapt these example paths to the real school account:

```text
~/campus-private/
  config.php
  campus.sqlite              # SQLite only; generated by setup
  setup.php
  schema.sqlite.sql
  schema.mysql.sql
  seed.json
~/public_html/campus/
  index.html
  assets/
  api.php
  .htaccess
```

`api.php` defaults to finding `../../campus-private/config.php` relative to its own directory. With the arrangement above that is outside `public_html`. If the school uses another layout, set `CAMPUS_CONFIG` in the server environment to the absolute private config path or adjust the one config-path line in the adapter. Never put a real config, database, SQL setup script or source archive in a publicly downloadable folder. Restrict private files/directories to the account and the necessary PHP process according to the school hosting instructions.

## Initialize the database

1. Copy `deploy/config.example.php` to the private folder as `config.php`.
2. SQLite: leave the SQLite DSN and ensure PDO SQLite and private-directory write access are available. MySQL: use the database provided by the university, enter its DSN/user/password in this private file, and ensure its default storage engine supports foreign keys (InnoDB).
3. Copy `deploy/setup.php`, both SQL schemas and `deploy/seed.json` into that same private folder. Run setup through a trusted SSH terminal. Never expose setup as a browser endpoint.
4. Provide `CAMPUS_ADMIN_EMAIL` and `CAMPUS_ADMIN_PASSWORD` as temporary environment variables, then run `php setup.php /absolute/path/to/campus-private/config.php`. Clear the variables afterwards. Do not put secrets in source control or command arguments. No known default administrator password is shipped.
5. Setup creates schema and sample content only once; rerunning does not reset existing data. If an admin email already exists, it is not silently promoted or reset. An administrator can promote a registered user through a prepared SQL update in the private database administration environment. Public registration never permits role selection.
6. Upload only the contents of `build/mercury/` to the assigned web directory. In an SFTP client, enable visibility of dotfiles to include `.htaccess`. If the host prohibits `Options`/header overrides and returns HTTP 500, follow the school configuration rules and remove the unsupported directives; the app does not rely on rewrite rules.

The PHP adapter uses PHP password hashes, native server sessions, parameterized SQL, request validation, origin checks and role/ownership enforcement. The Node and PHP implementations use different password/session formats. Do not copy the local Node database as a substitute for initializing the PHP deployment.

## Verify before submission

- Open the assigned HTTPS Mercury URL and verify assets and navigation under the actual subfolder.
- Request `api.php?path=/health` and confirm a successful database response; it exposes no credentials.
- Register a fresh test student; verify like/register/join and their persistence after logout/login.
- Log in as the privately created administrator; create/edit/delete a temporary event and club.
- Confirm a student cannot reach the management workspace and cannot modify content through the API.
- Confirm database/config URLs are not publicly accessible, and check host error logs without publishing them.
- Test mobile, tablet and desktop; verify the calendar and downloaded `.ics` file.
- Include the actual Mercury URL in the group handoff and Canvas submission.

SQLite and PHP were validated locally. No university host or MySQL server was accessible during implementation, so the Mercury environment and MySQL branch remain deployment checks.
